## 部署实测修订（2026-10-25 首次部署抓到的四个坑，按此执行不再踩）

1. **DSH 入口**：`@deepseek-ai/dsh@0.1.2-rc.1` 的 bin 是 `lib/bin.js`（不是 `bin/dsh.js`）；
   web profile 默认 `patchReload: live` 会因缺 Cordis HMR 崩溃 —— 首启后把
   `~/.dsh/profiles/web/package.json` 的 `"patchReload"` 改成 `"startup"` 再重启。
2. **NapCat Linux 启动配方**（官方 napcat-linux-launcher 非侵入注入）：
   - `libnapcat_launcher.so` 需用 g++ 现编（`-shared -fPIC launcher.cpp -o libnapcat_launcher.so -ldl`）；
   - **cwd 必须是 QQ 根目录**（注入器拦截相对路径 `resources/app/package.json`），launcher 里 `cd /opt/napcat-qq`；
   - `NAPCAT_BOOTMAIN` 指向 **NapCat 解压目录的上层**（代码里会拼 `./napcat/napcat.mjs`）；
   - QQ 版本硬要求 build ≥ 53644（3.2.34）：服务器原 /opt/QQ 是 52194 且与泠娜栈共享，**不升级、不动它**，
     解包 deb 到独立目录 `/opt/napcat-qq` 使用。
3. **旧 state 必须清洗**：tar 上传若带上封存包的 state/，旧 sessions.json 的会话映射会让 DSH follow 流
   每秒刷"流终结(error)"——首启前确认 state/ 除 bridge.log 外为空。
4. **单文件热修上传**：`tar czf - qq-bridge/src/core/xxx.js | ssh ... 'tar xzf - -C ~/qq-agent'` 后
   `sudo systemctl restart qq-agent-bridge` 即生效（git 先 commit 再传）。
5. **OneBot httpServers 必须开**（2026-10-25 深夜第 5 坑）：部署时把 NapCat 的 httpServers(3000) 关了只留
   WS(3001)，结果**桥自身收发没事、但 MCP 全套 napcat 工具全聋**——`mcp-host-server.js` 走
   `http://127.0.0.1:3000`（napcat_status 即 HTTP get_login_info），报 `reachable=false`。修法：
   `onebot11_<uin>.json` 的 `network.httpServers[0].enable=true`（**改配置不会热加载，必须重启
   qq-agent-napcat**），重启后 WS/HTTP 双端口起、桥自动重连。自查命令：
   `curl -s -H "Authorization: Bearer <token>" http://127.0.0.1:3000/get_login_info`。
6. **DSH 模型目录坑**：DSH 0.1.2-rc.1 的 `DEFAULT_MODELS` 不认识新发布的 `deepseek-flash` → 不按原生
   tools 协议发请求 → 模型把工具调用写成 DSML 正文（如幻觉工具名 `napcat_get_tool_schema`），桥按
   "正文未走发送工具"丢弃 → 用户只看到已读不回。修法：`~/.dsh/profiles/web/cordis.patch.yml` 预置
   `llm-deepseek.models` 覆盖数组（四个现役模型全列），重启 DSH。验证三板斧：
   ① RPC 探目录 `POST /api/session/modelCatalog`（先 GET `/?token=<日志尾token>` 换 cookie）；
   ② 建测试会话发"调用 napcat_status"看原生 `tool-call` 事件（落盘
   `~/.dsh/sessions/<home-tag>/session-*.jsonl.zstd`，zstd -dc 解开 grep tool-call）；
   ③ 桥日志确认无"模型正文未通过发送工具发出"。
   另注：模型名 `deepseek-v4.1-flash` 已被官方 API 拒（现役目录仅 `deepseek-flash`/`deepseek-v4-pro`）。
7. **密码重置后的连环坑（2026-10-26 亲历）**：改 QQ 密码会作废服务器登录态（NapCat 静默死，get_login_info
   都不通）；配 `ACCOUNT`+`NAPCAT_QUICK_PASSWORD_MD5` 走密码回退时，**重置后短期内每次都要短信验证**，
   且验证只认 WebUI 流程回传（ti.qq.com 直链可完成腾讯侧验证但 NapCat 收不到回调）——此时直接走扫码
   （临时从 env 移除 ACCOUNT/QUICK_PASSWORD 两行再重启 napcat 即出码），密码 env 留着等风控冷却再用。
   注意 napcat 单元要加 `EnvironmentFile=` 才会读 env（默认没有）。
8. **富媒体风控**：新登录态（尤其密码重置后）文件上传会报 `rich media transfer failed`，文本消息不受影响
   ——不是桥的 bug，重新扫码登录即恢复。判断法：用 send-docx 老路径对照测试。
9. **qq_send_file（代码工程交付，2026-10-26）**：`POST /api/social/send-file` + MCP `qq_send_file`，把
   DSH workspace 里的产物文件直读上传（内容零 token）。前置：config.json `dsh.workspaceRoot`（服务器已配
   `/home/ubuntu/qq-agent/dsh`；未配置则端点 fail-closed 503）。安全实测：越界 403/软链与 ../ 穿越 403/
   不存在 404/正向送达。**改 mcp-napcat-safe.js 后必须重启 qq-agent-dsh** 才进工具表（表在 MCP 握手时
   定型，93→94 实测）。curl 实测要带**双层** token：`x-console-token`（全局中间件）+ `x-agent-token`
   （会话令牌，social-state.json 里可取）。
10. **subagent 委派启用（2026-10-26）**——四个坑踩全了才通，正确做法是三处配置：
    ① **不要往 profile package.json 的 bundles 里加** `@deepseek-ai/dsh-subagent` 等——这些是纯库包
    （无 `dsh.bundle` 声明），加了直接启动崩（"declares no dsh.bundle"）；它们**dsh-base 本来就传递加载**
    （dsh-base/cordis.patch.yml 334-358 行），无需手动装载；
    ② 真正缺的是 **qq-chat preset 没挂载 tool-subagent**（原群聊设计"零本地工具"）：在
    `dsh/agent-presets/qq-chat/agent.cordis.yml` 加 entry（provider: spawn / toolName: subagent /
    modelSelectionSettings: true / backgroundMode: one-shot / maxDepth: 2），同步到
    `~/.dsh/.agent-presets/qq-chat/`；
    ③ **qq-tool-restrict.mjs 的 SAFE_EXACT 放行** `subagent` 与 `list_subagent_models`（执行期白名单）；
    ④ **模型选择要宿主授权**：`~/.dsh/settings.yaml` 加 `subagent-model-selection: {enabled: true,
    allowedModels: [{provider: deepseek-official, model: deepseek-flash}, {… deepseek-v4-pro}]}`——
    不加则 subagent 工具不暴露 provider/model/reasoning_effort 参数（无已记录策略的会话保持禁用）。
    另：cordis.patch.yml 顶层 `- name:` 是**插件加载**、`- id:` 是**配置覆盖**，两码事；patch.yml 的
    YAML 里 `@` 开头的值必须引号（heredoc 会吃单引号，用文件写入而非 shell 拼接）。
    验证：probe 会话让它「用 subagent 委派算 17*23，指定 v4-pro」——工具调用 + 模型自报指定成功。
    架构：主会话保持零本地工具，subagent 是唯一执行通道（沙箱/深度≤2/模型白名单），产物文件走
    qq_send_file 送回——「外包」即安全边界。
11. **preset 双路径坑（2026-10-26 友谊记忆部署亲历）**——只改仓库里 `dsh/agent-presets/qq-chat/agent.cordis.yml`
    **不生效**：DSH 实际读 DSH 家目录副本 `~/.dsh/.agent-presets/qq-chat/agent.cordis.yml`（坑 10 ②顺带提过，
    这里正式记：忘记同步 = 白改+白重启）。正确部署 = 仓库改 → `cp` 到 `~/.dsh/.agent-presets/` → pyyaml 校验 →
    查在途回合后重启 qq-agent-dsh → probe 验证条款真进了 system prompt。probe RPC 配方：token 取
    `~/.dsh-web.log` 尾（`grep -aoE "token=[A-Za-z0-9._-]+"`）→ `GET /?token=` 换 cookie →
    `POST /api/session/create` body `{type:'client-request',rpcId,method:'session/create',payload:{args:{request:{agentPreset:'qq-chat'}}}}`
    （sessionId 在 `result.value` 下，多一层 value）→ `POST /api/session/prompt` content `[{type:'text',text}]`；
    会话落盘 `~/.dsh/sessions/<tag>/<sessionId>/session.jsonl.zstd`，`zstd -dc` 后 grep 条款名与
    `"type":"tool-call"` 事件（工具表清单里每个工具名也会出现一次，别拿它当调用证据）。
12. **maxTokens 目录项与 DeepSeek API 硬顶（2026-10-26）**——单次回复输出上限默认 256K，来自 llm-deepseek
    适配器默认（`config.maxTokens ?? 256e3`）；覆盖入口 = `~/.dsh/profiles/web/cordis.patch.yml` 的
    `llm-deepseek → models:` 各模型项加 `maxTokens:`（优先级：目录项 > 全局 config > 适配器默认）。
    **API 硬顶 393216**：设 1000000 实测整轮报错 `valid range of max_tokens is [1, 393216]`（该回合无任何
    输出）——改此值必须 probe 冒烟（看 request/header 的 maxTokens + turn/end + 无 error）再收工。
    最终定值 **131072**（2026-10-26 二次定规）：上限的意义在失控熔断而非赋能——合法产出永远碰不到顶
    （最重合法单轮 ≈5 万 token：超大 pptx/docx 工具参数载荷；推理另有记账不占此额），128K 留 2.6 倍余量，
    失控打磨时长较 393216 缩约 3 倍；真撞顶（表现为报截断）再按本坑流程调。
13. **沙箱读白名单 patch（2026-10-26 凭据审查后加固）**——DSH `workspace-write` 模式的白名单**只管写**：

    bridge env 含 API key）、/home 非 workspace、/var /root /opt。

14. **交付断链三重根因（2026-10-26 修复落地后首次真实任务实测抓出）**——QQ 里任务能跑完但文件发不出：
    ① **目录拧巴**：桥会话 sessionCwd 默认 = state/agents（沙箱写边界跟随 session cwd），而
    qq_send_file 白名单 = dsh.workspaceRoot（另一目录）→「子代理能写的发不出」；probe 回归没踩到
    是因 probe 会话 cwd 恰好 = workspace。修复 = config.json 顶层 `"sessionCwd": "<workspaceRoot>"`
